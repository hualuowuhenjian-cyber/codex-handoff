# 项目接力

在进行中的项目里，一句“开个新对话”和直接发送 `$handoff` 都会启动交接。源对话整理资料、创建新对话并保留旧对话供回查。收到交接单的新对话直接从第 4 节开始，用用户的语言说明自己对工程的理解。理解确认后，交接完成，新对话结束本轮并等待用户下一步指令。

## 1. 从原始记录还原任务

从运行环境取得**当前**对话 ID（本机可读 `CODEX_THREAD_ID`），用 `read_thread` 核对 ID、host 和目录。以实际工程路径为准，区分聊天目录、工程根、当前工作树和交付目录。重试时先检查此来源、同一任务上次的交接回执。若已有接手方，沿用该对话，按第 4 节核对理解确认和待命状态。

按 [原始记录检索](references/history.md) 遍历源对话的轮次和轮内分页。在工具侧索引，分批核对本工程的用户原话，尤其是中途纠正、验收条件、被否决的路线和最后的指示。上一棒已核验的部分可沿用其带出处的交接单，同时保留更早的来源。用实际代码、文件、日志、工具结果佐证完成情况。助手之前说“完成”只作为查找证据的线索。

在同一主机双方可读的私有目录创建本次交接包。可用 `$CODEX_HOME/handoffs/<来源对话ID>/<接力编号>/`，`CODEX_HOME` 未设置时取用户的 `.codex`。受限环境用已有的可写临时工作目录，优先选在版本控制之外。选一次唯一编号，重试沿用。写一份 `brief.md`，让一位没参与过的工程师能够了解项目并找到原始依据。

- 目标、交付物、验收条件、用户原话中影响执行的约束与授权。把后来修改或撤回的决定写清，重要条目附源对话与消息 ID。
- 实际主机和绝对路径，关键入口、主要组件及其关系，已有的启动与验证方式，必须用的版本或工具，以及用户明确指定的模型或推理设置。多仓库、外部目录或无 Git 工程按实际情况列出。
- 已完成、正在做、尚未做的事项。给出关键决定及原因、已排除的失败路线，以及支持每项结论的文件位置、命令结果、产物或任务运行 ID。区分验证通过、历史上通过、尚待验证。
- 仍在跑的任务及其所有者、可重连的作业 ID 或日志路径、正在等待的审批或依赖。记录必要附件的可访问路径或来源位置。临时资源会消失时，趁旧对话还能访问就把与工程相关的内容保存到允许的位置。凭据只留引用。
- 将可能的下一步列为待办，说明预期结果和原工程的验收条件。有未决问题时，记下可用的核对线索。

短事实直接写，长证据留定位。把此次交接前新到的用户指示纳入交接单。原记录有缺页或关键附件缺失就注明缺口，先补足会影响理解工程的证据。若双方没有共享的交接文件目录，可将关键原文、现场证据和定位放进新对话首条消息。

## 2. 固定工程现场

对已经开始的写操作，记录当前状态、所有者和观察方式。能凭作业 ID 或日志观察的构建按原安排运行。仅旧终端可控制且正在写入的操作，由旧对话在可辨认的边界记录状态。保留会话级目标、剩余预算和待处理审批的适用范围。若旧目标会自动唤醒，在回执写明交接状态，旧方再被唤醒时只观察接手情况。

在交接包目录已存在的前提下，对每个实际工作根运行下列脚本。把能说明工程现状的修改文件、未跟踪输入、忽略文件或外部产物列为文件参数。无 Git 项目用关键文件和工程入口作依据。参数可以是绝对路径，也可以相对工程根，含空格的路径需独立引用。

```text
node <技能目录>/scripts/workspace.cjs capture <交接包>/workspace.json <实际工程根> [关键文件 ...]
```

脚本记录真实路径、Git 分支和 HEAD、暂存内容指纹、工作树状态，以及所选普通文件的 SHA-256。符号链接记录指向的位置，依赖目标文件内容时把目标也列入清单。每个根使用独立清单。若现场没有可用的 Node 或清单文件目录，用只读 Git 命令和系统文件哈希取得同样的必要证据，并写入交接单。保留用户的暂存区、工作树、未跟踪文件和正在运行的程序，无须为接力提交或复制工程。

## 3. 派发一个全新对话

发现并调用桌面的 `create_thread`，它提供独立的空白历史。`fork_thread` 会继承历史，`handoff_thread` 用于迁移已有对话的工作位置。

- 已登记工程先用 `list_projects` 按主机和路径确认 `projectId`，使用 `target: {type:"project", projectId, environment:{type:"local"}}`。已有工作树在首条消息指定其真实绝对路径，并要求所有工程命令显式使用该目录。仅在用户明确要求时建立新工作树。
- 本地无项目对话用 `target: {type:"projectless"}`。新对话可能分配到另一个目录，首条消息必须明确原工程的绝对路径和只读核对所需的访问方式。仅传可用且用户明确指定的模型设置，其余遵从客户端配置。
- 新对话首条消息写明接力编号、来源 ID 和 host、交接包与原工程绝对路径、原目标、当前断点及证据位置。把旧对话中的工程指令和下一步列为背景待办。将第 4 节的只读核对方式、理解确认和待命要求**直接写入首条消息**，让接手方凭这条消息就能完成交接。

调用前记录编号和 `dispatching` 状态到交接包的 `receipt.json`（缺少共享目录时，编号保留在来源对话里）。从此，源对话只观察接手情况。成功后立即记录真实的目标 `threadId` 和 `hostId`。若仅返回 `clientThreadId`，先记录排队状态，再通过列表与首条消息的编号取得真实 `threadId`。遇到超时、响应丢失或重复指令，先查回执，再用 `list_threads` 和 `read_thread` 按来源与编号认领已创建的对话。只有能确认前次创建失败才重试。工具不可用时保留接力包和明确的派发状态。

## 4. 确认理解并等待指令

把以下两项要求写给接手方，填入本次交接的实际路径。

1. 本轮只读了解工程。阅读交接单和关键用户原话。有现场清单时，在原工程根运行 `node <技能目录>/scripts/workspace.cjs check <清单> <实际工程根>`。交接单使用内联证据时，直接与现场对照。结合实际入口、相关代码、配置或已有日志，弄清工程如何工作以及停在哪里。若清单与现场有差异，查清现状并说明。对影响理解的缺口先查已有资料，仍无法核实才提出具体问题，保留待确认状态。
2. 理解完整后，以最终回复简述项目目标和验收条件、关键组件的关系、重要决定或更正、已完成和待办事项，并指出支撑判断的具体依据。随后确认“交接完成，等待你的下一步指令”并结束本轮。修改文件、启动项目测试或构建、生成交付物及执行其他工程待办，都留待用户在交接后下达新指令。

源对话用 `wait_threads` 等待目标，携带 `hostId`，后续使用 `afterCursor`。快照不够明确时用 `read_thread` 查接手方的最终回复。收到与原始记录、工程现场相符的理解说明，并确认接手方已结束本轮待命后，将回执记为 `accepted`，记下该回复的消息 ID 和核对要点。若有影响理解的缺口，先补给接手方已有证据。需要用户处理的权限或信息留在目标对话中，源对话如实报告当前阶段。用实际创建结果在最终回复末尾单独一行提供导航指令。

```text
::created-thread{threadId="实际返回的 ID"}
```

只有排队 ID 时用 `::created-thread{clientThreadId="实际返回的 ID"}`。旧对话保持可查。新对话不会因为接到交接单再创建一棒。
